# 词汇语法评分性能优化

更新时间：2026-07-28

## 目标与范围

本文记录词汇练习和语法练习在多用户并发下的评分热路径优化。

本轮目标是缩短每次提交评分所需的数据库访问次数，同时保留以下业务语义：

- FSRS 评分完成后，复习卡片状态立即可读取。
- FSRS 卡片状态在请求完成前写入；每日练习日志和学习计划计数通过可靠 outbox 最终入账。
- 词汇本、语法错题本和收藏状态的已有行为不变。
- 通用复习接口仍会校验题目存在性。

本轮不改变 FSRS 算法参数、复习间隔计算或前端接口路径。日统计由立即一致改为短暂最终一致；尚未在服务器完成压测，因此本文不把任何预估降低的时延写成已达成的性能结果。

## 优化前的关键路径

### 词汇评分

```text
POST /api/vocabulary/practice-ratings
  -> 查询用户
  -> 校验 vocabulary 存在
  -> 查询 user_wordbook
  -> 首次学习时插入 user_wordbook
  -> ReviewService 再次校验 vocabulary 存在
  -> 查询 user_word_progress
  -> FSRS.review(...)
  -> 保存 user_word_progress
  -> 写入每日练习去重日志
  -> 学习计划 INSERT ... ON DUPLICATE KEY UPDATE
  -> 查询学习计划
  -> 当日进度 INSERT ... ON DUPLICATE KEY UPDATE
  -> 更新当日词汇完成数
```

### 语法练习

语法页面对一题通常会发起两类请求：

```text
POST /api/grammar/practice-results
  -> 查询用户、校验题目
  -> 查询/保存 user_grammarbook
  -> 写入每日练习去重日志和当日进度

POST /api/grammar/practice-ratings
  -> 查询用户、校验题目
  -> ReviewService 再次校验题目
  -> 查询/更新 user_word_progress
```

FSRS 本身只有少量内存浮点计算，不是主要耗时来源。热路径的主要成本是多次数据库往返、首次记录的“先查再写”，以及同一用户同一天并发提交时对当日进度行的竞争。

## 已完成优化

### 1. 词汇本改为原子登记

文件：

```text
backend/src/main/java/com/englishlearningcopilot/backend/repository/UserWordbookRepository.java
backend/src/main/java/com/englishlearningcopilot/backend/service/impl/VocabularyServiceImpl.java
```

词汇评分不再先查询 `user_wordbook` 再决定是否插入，改为单条原子 SQL：

```sql
INSERT INTO user_wordbook (user_id, vocabulary_id, favorited)
VALUES (:userId, :vocabularyId, FALSE)
ON DUPLICATE KEY UPDATE user_id = user_id
```

语义：

- 首次练习该词时，创建词汇本记录，默认未收藏。
- 已有记录时，不修改任何业务字段，尤其不覆盖 `favorited`。
- 同一用户同一单词首次并发提交时，唯一约束负责去重，不再有“两个请求都查不到、随后同时插入”的应用层竞态。

### 2. 语法作答结果改为原子写入

文件：

```text
backend/src/main/java/com/englishlearningcopilot/backend/repository/UserGrammarbookRepository.java
backend/src/main/java/com/englishlearningcopilot/backend/service/impl/GrammarServiceImpl.java
```

语法作答不再查询并加载 `user_grammarbook` 实体后再保存，改为：

```sql
INSERT INTO user_grammarbook (user_id, grammar_question_id, favorited, incorrect)
VALUES (:userId, :grammarQuestionId, FALSE, :incorrect)
ON DUPLICATE KEY UPDATE incorrect = :incorrect
```

语义：

- 首次作答创建记录，默认未收藏，并写入本次对错结果。
- 再次作答只更新 `incorrect`，保留已有 `favorited`。
- 与此前 `setIncorrect(...)` 后保存实体的效果一致。

### 3. 取消评分流程中的重复题目校验

文件：

```text
backend/src/main/java/com/englishlearningcopilot/backend/service/ReviewService.java
backend/src/main/java/com/englishlearningcopilot/backend/service/impl/VocabularyServiceImpl.java
backend/src/main/java/com/englishlearningcopilot/backend/service/impl/GrammarServiceImpl.java
```

词汇和语法业务服务已经在调用 FSRS 前校验词或题存在，因此评分流程改为调用：

```java
submitValidatedVocabularyRating(...)
submitValidatedGrammarRating(...)
```

通用复习接口仍调用原有的：

```java
submitRating(...)
submitGrammarRating(...)
```

它们保留存在性校验。因此这项优化只消除已验证业务流程中的重复查询，不降低对外通用接口的校验能力。

### 4. 已有学习计划不再每次无效 upsert

文件：

```text
backend/src/main/java/com/englishlearningcopilot/backend/service/impl/LearningPlanServiceImpl.java
```

此前 `getOrCreatePlan` 每次都会先执行默认计划 upsert，再查询计划。现在的常规路径先查已有计划；仅在旧用户确实缺少计划记录时，才创建默认计划并再次读取。

```text
已有计划：SELECT plan
缺少计划：SELECT plan -> INSERT ... ON DUPLICATE KEY UPDATE -> SELECT plan
```

这不会改变自定义每日目标。已有用户仍使用数据库中自己的词汇和语法每日目标创建或更新当天进度。

### 5. 每日统计改为事务内 outbox、后台可靠入账

文件：

```text
backend/src/main/java/com/englishlearningcopilot/backend/entity/LearningProgressOutboxEvent.java
backend/src/main/java/com/englishlearningcopilot/backend/repository/LearningProgressOutboxEventRepository.java
backend/src/main/java/com/englishlearningcopilot/backend/service/LearningProgressOutboxService.java
backend/src/main/java/com/englishlearningcopilot/backend/service/LearningProgressOutboxProcessor.java
backend/src/main/java/com/englishlearningcopilot/backend/service/LearningProgressOutboxScheduler.java
```

词汇评分和语法作答结果不再直接写 `user_daily_practice_log`、学习计划和当天进度。它们改为在原有业务事务内写一条唯一的 outbox 事件：

```text
词汇：校验 -> 词汇本原子登记 -> FSRS 更新 -> 写 outbox -> 提交 -> 返回评分成功
语法：校验 -> 错题本原子写入 -> 写 outbox -> 提交 -> 返回作答成功
```

词汇的 FSRS 仍然同步；语法保持原有产品语义，即用户提交作答结果时计入练习，而不是等待其稍后选择评分。

事件唯一键为：

```text
(user_id, plan_date, practice_type, item_id)
```

重复提交同一题时，数据库只保留一条事件。评分事务与 outbox 插入使用同一个数据库事务，因此：

```text
前端收到评分/作答成功
<=>
FSRS（词汇）或作答结果（语法）已提交，且待入账事件也已持久化
```

后台默认每 200ms 拉取最多 50 条就绪事件，并以 30 秒数据库租约领取：

```text
PENDING -> PROCESSING（租约） -> COMPLETED
                         |
                         +-> 失败：PENDING，按 1~60 秒退避后重试
```

服务重启时，超过租约的 `PROCESSING` 事件可被其他实例或重启后的实例重新领取。消费者的入账事务仍先调用 `user_daily_practice_log` 的唯一键去重，再递增当日进度：

```text
首次消费：插入练习日志 -> 增加日进度
重复消费：练习日志已存在 -> 不再增加日进度
```

因此实现的语义是“至少处理一次、效果等同一次”，而不是依赖不可靠的内存 `@Async`。即使进程在“进度已提交、事件尚未标记 COMPLETED”之间退出，重试也只会命中已有练习日志，不会二次计数。

一致性边界变为：

| 立即一致 | 短暂最终一致 |
| --- | --- |
| 词汇 FSRS 难度、稳定度、到期时间 | 今日词汇/语法已练数量 |
| 语法作答正确/错误状态、错题本 | 学习计划完成状态、连续学习天数 |
| 评分/作答接口成功或失败 | 首页、个人主页、仪表盘聚合统计 |

正常无积压时，统计会在一次轮询周期内开始处理；失败或积压时统计可能延后，但事件留在数据库等待重试，不会静默忽略题目。可用配置：

```properties
app.learning-progress-outbox.scheduler-enabled=true
app.learning-progress-outbox.poll-interval-ms=200
```

测试环境关闭调度器，避免后台线程抢占集成测试事件；消费者仍通过测试直接调用。

## FSRS 逻辑边界

本轮 upsert 不用于 FSRS 卡片。

```text
user_wordbook      词汇本登记、收藏状态
user_grammarbook   错题本结果、收藏状态
user_word_progress FSRS 卡片状态
```

FSRS 仍按既有流程执行：

```text
读取 user_word_progress
  -> FSRS.review(card, rating)
  -> 写回 difficulty、stability、interval、reps、lapses、due、last_review
```

因此，词汇本和错题本的原子写入不会跳过、合并或覆盖 FSRS 评分计算。

## 当前仍存在的并发边界

### 同一用户、同一题的 FSRS 并发评分

`user_word_progress` 当前仍采用：

```text
SELECT 旧卡片状态 -> 内存 FSRS 计算 -> SAVE 新卡片状态
```

若同一用户在多个标签页或因网络重试对同一题并发提交，两个请求可能读取同一旧状态，后提交者覆盖先提交者的计算结果。本轮没有改变此行为，也没有用词汇本/错题本 upsert 直接替代 FSRS 更新。

后续应单独评估：

- 在 `UserWordProgress` 添加乐观锁版本号。
- 对乐观锁冲突进行有限重试。
- 为客户端评分请求增加 `attemptId`，区分“网络重试”与“用户确实进行了第二次评分”。

### 同一用户、同一天的学习进度热点

每条新练习仍需更新：

```text
user_daily_learning_progress(user_id, plan_date)
```

同一用户的事件在入账时仍会更新这一行，因而 InnoDB 仍会串行化同一用户当天的计数；区别是锁等待不再阻塞评分/作答 HTTP 请求，而只会形成后台 outbox 积压。当前消费者按单线程批次执行，优先保证计数顺序和幂等性；若服务器压测显示积压持续增长，再评估按用户分片或受控并行消费。

需要在生产监控中关注：`PENDING` 事件数量、最旧 PENDING 事件年龄、重试次数和 `last_error`。当前尚未新增监控面板或告警规则。

其中 `LearningProgressOutboxIntegrationTest` 使用真实 H2 数据库验证：

- 消费两次后只有一条每日练习日志，且当天词汇计数只增加一次。
- 事件最终进入 `COMPLETED`，并记录处理时间。

`LearningProgressOutboxProcessorTest` 还覆盖正常完成和统计写入抛错后重新调度两条路径。

## 服务器压测计划

压测将在服务器环境完成，且应将以下三种工作负载分开，避免把同用户行锁误判为多用户吞吐不足：

| 场景 | 用户分配 | 验证目标 |
| --- | --- | --- |
| 独立用户评分 | 每个 VU 使用独立账号 | 真实多用户吞吐和连接池等待。 |
| 同用户、不同题并发 | 多个请求共享同一账号但题目不同 | 当日学习进度行锁的影响。 |
| 同用户、同题并发 | 多个请求共享同一账号和题目 | FSRS 卡片写入竞争和幂等性。 |

现有 `performance/k6/vocabulary-register-practice-chain.js` 已可用 `USER_PREFIX + __VU` 为每个 VU 生成独立用户。旧词汇/语法链路脚本默认复用有限账号池，不应直接把高 VU 的结果解释为“高独立用户并发”。

服务器上至少记录：

```text
各评分接口 p50 / p95 / p99
HTTP 错误率
Hikari active / idle / pending 连接数
MySQL 慢查询
MySQL InnoDB 行锁等待和死锁
CPU、内存、磁盘 IO
```

在确认瓶颈前，不应仅靠增大 Hikari 连接池解决问题。当前未显式配置 Hikari 最大连接数，需结合服务器 MySQL 容量和实际 pending 指标再决定参数。

## 后续优先级

1. 在服务器完成上述三类压测，形成优化前后同条件报告。
2. 若同题并发存在冲突，实施 FSRS 乐观锁和有限重试。
3. 在服务器压测中记录 outbox 积压、事件处理年龄、重试和日进度行锁；确认默认 200ms/50 条批次是否足够。
4. 若同用户事件积压持续增长，评估按用户分片或受控并行消费者，继续以练习日志唯一键保证幂等。
5. 若独立用户下连接池 pending 持续增长，再调优 Hikari 和 MySQL 连接容量。
