# 口语测评性能优化

## 目标与范围

本文针对网页端“进入口语会话”和“停止录音后等待下一句回复”两个加载慢的体验问题，说明当前调用链、已完成的优化、运行配置、验证方法和后续方案。

本次不改变评分规则、场景数据或接口路径。优化目标是缩短用户必须等待的关键路径，并让耗时的发音评分与语音合成不阻塞文字对话。

## 当前调用链

### 创建会话

```text
POST /api/speaking/sessions
  -> 创建 speaking_session
  -> 写入场景开场消息
  -> 返回 session 与 messages
  -> 后台生成开场消息 TTS
```

### 提交一轮录音

```text
浏览器 MediaRecorder 录音
  -> multipart 上传
  -> 保存原始音频
  -> FFmpeg 转为 16 kHz 单声道 PCM
  -> 讯飞文件 ASR 轮询并取得转写
  -> 保存用户消息
  -> 校内 DeepSeek 生成下一句文字回复
  -> 保存 Agent 消息并立刻返回 HTTP 响应
  -> 后台执行 TTS
  -> 后台执行 ISE 发音评分
```

对用户当前轮次的文字回复，真正串行且不可直接并行的部分是：

```text
上传/转码 + ASR + LLM
```

LLM 必须使用 ASR 转写文本，因而不能在转写完成前安全启动。ISE 评分和 TTS 都不影响文字回复，应该留在后台。

## 本次已完成优化

| 优化 | 位置 | 效果 |
| --- | --- | --- |
| 配置化开场句替代同步 LLM 开场 | `SpeakingServiceImpl#createSession` | 进入会话页不再等待一次 DeepSeek 网络请求；直接返回场景已配置的 `openingMessage`。 |
| 开场 TTS 保持异步 | `SpeakingAgentAudioSynthesisService` | 页面先显示并可继续操作，语音生成不会卡住 `POST /sessions`。 |
| 逐轮 ISE 默认异步 | `SpeakingServiceImpl`、`SpeakingPronunciationEvaluationService` | 评分仍会写回用户消息，但不阻塞下一句 Agent 文本。 |
| Agent TTS 事务提交后异步排队 | `SpeakingServiceImpl`、`SpeakingAgentAudioSynthesisService` | 避免把 TTS 网络等待加入录音提交接口的响应时间。 |
| TTS 结果立即刷新 + 800 ms 轮询 | `SpeakingConversationPage` | 收到 `audioPending` 后先立即查询一次，随后每 800 ms 查询；减少 TTS 已完成但前端仍等待固定 1.2 秒轮询周期的空档。 |
| 限制 LLM 上下文 | `SjtuDeepSeekSpeakingAgentClient` | 仅保留最近 8 条消息，较早记录压缩为最多 600 字符；减少请求体和模型上下文处理时间。 |
| 限制模型生成上限 | `application.properties` | 默认 `max-tokens=120`，符合“下一轮一句或两句 + 可选即时提示”的实际输出需求，防止异常长回复拖慢生成。 |

其中前两项是本次新增的首屏优化；其余项为当前代码中已启用或已配置的关键路径优化，集中记录在这里便于部署和回归。

## 配置建议

生产或联调环境保持以下默认值，除非有明确的效果验证：

```properties
# 用户每轮文字回复不等待 ISE。
speaking.pronunciation.evaluate-on-turn=false
speaking.pronunciation.evaluate-async=true

# 控制 DeepSeek 上下文与输出长度。
speaking.agent.sjtu.max-tokens=120
speaking.agent.sjtu.history-message-limit=8
speaking.agent.sjtu.history-context-max-chars=600

# 讯飞文件 ASR 的状态检查间隔；不要在没有供应商压测数据时随意降得过低。
xfyun.asr.poll-interval-ms=500
```

环境变量形式分别为：

```text
SPEAKING_PRONUNCIATION_EVALUATE_ON_TURN=false
SPEAKING_PRONUNCIATION_EVALUATE_ASYNC=true
SJTU_AI_MAX_TOKENS=120
SJTU_AI_HISTORY_MESSAGE_LIMIT=8
SJTU_AI_HISTORY_CONTEXT_MAX_CHARS=600
XFYUN_ASR_POLL_INTERVAL_MS=500
```

不要把 `SPEAKING_PRONUNCIATION_EVALUATE_ON_TURN` 改成 `true` 作为默认值。这样会让 ISE WebSocket 评分重新进入每轮用户等待路径。

## 观测与验收

后端日志已经输出以下关键耗时：

```text
Speaking turn processed: asrMs, iseMs, llmMs, totalMs
Speaking TTS completed: durationMs, audioReady
```

验收时按同一网络和同一场景分别记录至少 20 次会话进入与 20 轮录音提交，统计 p50、p95 和失败率。建议单独记录：

| 指标 | 含义 | 当前关注点 |
| --- | --- | --- |
| 会话创建耗时 | `POST /sessions` 完成时间 | 不应再包含 LLM 网络时间。 |
| `asrMs` | 上传后到获得转写的耗时 | 通常是逐轮文字回复的最大瓶颈。 |
| `llmMs` | 转写后到获得 Agent 文字的耗时 | 受模型、网络、上下文和输出长度影响。 |
| `totalMs` | 整轮文字回复耗时 | 近似为 ASR + LLM 加上少量本地处理。 |
| TTS 完成耗时 | Agent 文本出现到可播放音频 | 不应阻塞文本显示或下一轮录音。 |

在没有采集真实环境样本前，不应把估算时延写成已达成的性能数据。

## 下一阶段方案

### 优先级 P0：缩短 ASR 的等待模型

现有讯飞文件 ASR 必须“完整上传 -> 转码 -> 创建订单 -> 轮询完成”，用户说得越长，首个可用文本越晚。下一阶段应评估讯飞实时流式 ASR 或兼容的 WebSocket ASR：

```text
浏览器分片录音
  -> WebSocket 推送 PCM/Opus 分片
  -> 服务端获取 partial transcript
  -> 停止录音后只等待 final transcript
  -> 调用 LLM
```

收益是明显缩短停止录音后的 ASR 尾部等待；代价是需要会话状态管理、断线重连、最终文本去重和更多真实设备测试。该项尚未实现。

### 优先级 P1：LLM 首 token 流式返回

DeepSeek 端若支持 OpenAI-compatible SSE，可让后端将 Agent `content` 流式推给前端。前端应先渐进展示文字，最后再保存完整消息和发起 TTS。该项需要新的流式 API 或 SSE 通道，不能在当前单次 JSON 响应中无风险加入，尚未实现。

### 优先级 P1：缩短长事务

`submitRecording` 当前带有 Spring 事务注解，并在 ASR 与 LLM 网络调用期间持有事务上下文。高并发下应拆为短事务：

```text
短事务 A：校验会话并创建用户消息占位
无事务：保存音频、ASR、LLM
短事务 B：保存转写、Agent 回复和轮次
```

这项主要提升并发稳定性和数据库连接利用率，不会显著减少单个用户的 ASR 或 LLM 网络时延。需要处理同一会话的重复提交与顺序控制，尚未实现。

### 优先级 P2：异步可靠性与容量

- 为 TTS 与 ISE 队列增加队列深度、拒绝次数和任务耗时指标。
- 高并发部署时，使用对象存储替代本地 `uploads/speaking`，避免多实例读不到录音文件。
- 在供应商限流数据确认后，再决定是否将 `xfyun.asr.poll-interval-ms` 从 500 ms 下调到 300-400 ms；这最多降低轮询发现完成的尾部等待，但会增加轮询请求量。

### 容量预埋：多 Key / 多 API Route（默认关闭）

已新增一个不接入当前请求链路的 Route 配置与选择器，为后续多用户、多 Key 和多个兼容 API 服务做准备。默认：

```properties
speaking.routing.enabled=false
```

关闭时不会创建 Route 选择器，也不会修改当前 `SpeakingServiceImpl`、`SjtuDeepSeekSpeakingAgentClient`、ASR、ISE、TTS 或前端的任何调用路径。因此当前单 Key 的请求没有新增数据库访问、网络访问、队列、锁或运行时选择步骤。

未来显式开启后，Route 按 `LLM`、`ASR`、`ISE`、`TTS` 能力分别维护并发上限、在途任务数、延迟 EWMA、连续失败次数和冷却时间。选择器只分配一个 Route 租约，不执行外部调用、不自动重试；调用方仍需根据幂等性决定是否可以对 429、超时或网关故障执行故障转移。

在没有单 Key 开启模式下的回归数据前，不应把该选择器接到生产语音请求。

### 容量预埋：持久化口语轮次任务（默认 inline）

已新增 `speaking_turn_tasks` 任务表和状态枚举，为未来 `ASR -> LLM` 的排队、保序、重试和多 Route 分配提供持久化边界。当前默认模式为：

```properties
speaking.dispatch.mode=inline
```

`inline` 模式不会创建 `SpeakingTurnTaskService`，现有 `POST /api/speaking/sessions/{sessionId}/messages` 不读写任务表，继续使用当前同步链路。任务层因此不会为当前单 Key 的任何请求增加数据库读写或调度开销。

未来 `queued` 模式才会使用任务服务。任务的唯一键为：

```text
(session_id, attempt_id)
```

网页端现在会为每次录音生成稳定 `attemptId` 并作为 multipart 字段提交。`inline` 后端会忽略该额外字段，仍直接返回原有 `SpeakingTurnResponse`；只有排队模式的后端会使用它做幂等键。网络重试使用相同值时，会原子地返回同一个任务，而不是创建第二条 ASR/LLM 调用。

已预定义的主链路状态：

```text
PENDING -> TRANSCRIBING -> GENERATING_REPLY -> REPLY_READY
失败：TRANSCRIPTION_FAILED / REPLY_FAILED
```

TTS 与 ISE 继续作为不阻塞 Agent 文字回复的辅助任务，不纳入该主链路状态机。

排队模式已具备完整但默认关闭的单 Key 执行闭环：

```text
POST /messages + attemptId
  -> 202 Accepted + taskId
  -> 保存原始录音引用
  -> worker 以短事务领取任务
  -> 无事务执行 ASR
  -> 短事务写入 USER 转写
  -> 无事务执行 LLM
  -> 短事务写入 AGENT 回复并更新轮次
  -> GET /turn-tasks/{taskId} 返回 REPLY_READY + 原有完整 turn 响应
```

worker 会用会话行锁和创建时间/任务 ID 顺序保证同一个 session 的轮次不会并行乱序；ASR 失败在尚未写入用户消息时最多按 `speaking.dispatch.max-attempts` 重试一次，LLM 失败暂时作为终态返回，避免已经持久化转写后重复创建用户消息。LLM 的持久化阶段重试需要单独的回复幂等状态，后续再加。

前端收到 `202` 时每 750 ms 查询一次任务；收到 `REPLY_READY` 后仍按原有对象结构更新会话、播放 TTS。`inline` 模式不会进入这段轮询，也不会创建任务服务、worker 或任务记录。

不要直接在生产打开 `queued`。启用前至少在预发布环境使用单 Key 验证：连续录音、同一 attempt 的网络重试、会话内保序、worker 重启后的待处理任务，以及 p50/p95、失败率和积压深度。排队模式当前仍使用本机文件系统保存上传音频，多实例部署前必须替换为所有实例可读的对象存储。
