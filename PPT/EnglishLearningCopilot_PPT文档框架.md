### 页面标题

```text

```

模块级切换示例：

```text

VITE_AUTH_API_MODE=http
VITE_SPEAKING_API_MODE=mock
VITE_VOCABULARY_API_MODE=http
```

### 版式建议

- 下方放"页面组件只调用 useAppServices，不直接关心数据源"

### 讲述重点

这个设计支持多人并行开发——前端开发者可以先在 mock 模式下完成口语页面，等后端接口就绪后再切到 http 联调，不会被后端进度阻塞。

## 第 13 页：关键技术一：口语对话处理链路

### 页面标题

口语提交链路将同步体验与异步能力分离

### 页面内容

完整调用链：

```text
浏览器 MediaRecorder 录音
→ multipart 上传
→ 后端保存原始音频
→ FFmpeg 转为 16 kHz 单声道 PCM
→ 讯飞文件 ASR 轮询并取得转写
→ 保存 USER 消息
→ 校内 DeepSeek 生成下一句文字回复
→ 保存 AGENT 消息并立刻返回 HTTP 响应
→ 后台异步执行 TTS（不阻塞）
→ 后台异步执行 ISE 发音评分（不阻塞）
```

**关键链路区分：**

| 同步主链路（用户必须等） | 异步后台链路（用户不用等） |
|---|---|
| 上传 + 转码 + ASR + LLM 生成 | TTS 语音合成 |
| 返回 Agent 文字回复 | ISE 发音评分 |

设计约束：LLM 必须等 ASR 转写完成才能生成回复（依赖关系），因此 ASR→LLM 不可并行。但 TTS 和 ISE 都不影响文字回复，可以放在后台。

### 版式建议

- 上方流程图，用颜色区分同步（深蓝）和异步（浅灰）
- 下方用"同步主链路"和"异步后台链路"分成两条泳道
- 标注：用户只等左侧，右侧在后台悄悄完成

### 讲述重点

强调用户体验优化的核心判断：用户最关心下一句文字回复，所以发音评分和语音合成可以后台完成。这是一个"知道什么可以慢"的设计决策。

## 第 14 页：关键技术二：FSRS 与学习进度 Outbox

### 页面标题

复习算法与 Outbox 机制兼顾个性化和并发可靠性

### 页面内容

**FSRS（Free Spaced Repetition Scheduler）：**

- 根据用户每次评分（1-4），更新单词记忆状态
- 四参数模型：difficulty、stability、interval、due
- 评分低 → stability 下降、间隔缩短；评分高 → stability 上升、间隔拉长
- 支持个性化复习路径，每个人的复习节奏不同

**Outbox 事件机制：**

```text
评分/作答成功
→ 业务事务内写入唯一 Outbox 事件（PENDING）
→ 提交事务，返回评分成功（不等待统计）
→ 后台每 200ms 轮询消费 PENDING 事件
→ 30 秒数据库租约领取（PROCESSING）
→ 更新每日练习日志 + 日进度（COMPLETED）
→ 失败：退回 PENDING，1~60 秒退避重试
```

事件唯一键：`(user_id, plan_date, practice_type, item_id)` ——同一题重复提交只保留一条事件，消费时练习日志唯一键再次去重，确保"至少处理一次、效果等同一次"。

### 版式建议

- 左侧：FSRS 卡片状态流转图（评分 → 参数更新 → 下次复习时间）
- 右侧：Outbox 事件状态机：PENDING → PROCESSING → COMPLETED，失败路径回退
- 底部标注：进程崩溃后重启，超过租约的 PROCESSING 事件可被重新领取

### 讲述重点

说明项目考虑了并发和可靠性。Outbox 机制的价值在于：评分接口不需要等进度统计完成才返回，用户体验更好；同时通过唯一键和租约保证统计不丢不重。

| 难点 | 现象 | 根因 | 解决方案 | 效果 |
|------|------|------|----------|------|
| **进入会话慢** | 创建 session 要等数秒才能看到开场白 | LLM 生成开场白在同步路径上 | 场景预配置 `openingMessage`，跳过 LLM | 不再等待网络请求 |
| **录音后等太久** | 用户说完一句话到看到回复需 10+ 秒 | ASR、LLM、TTS、ISE 全部串行 | TTS/ISE 异步化；只保留 ASR→LLM 在关键路径 | 文字回复不再被语音合成阻塞 |
| **LLM 响应越来越慢** | 对话轮次多了以后回复明显变慢 | 上下文消息累积膨胀 | 限制最近 8 条消息 + 压缩为 600 字符 + `max-tokens=120` | 保持响应时间稳定 |
| **TTS 轮询滞后** | TTS 已完成但前端还在等固定间隔 | 轮询周期固定 1.2 秒 | 立即查询一次 + 800ms 快速轮询 | 减少音频就绪后的空档 |
| **音频格式不匹配** | 浏览器录音格式讯飞不认 | WebM/Opus ≠ 16kHz PCM | FFmpeg 服务端转码 | 统一为讯飞要求的格式 |

**设计决策的核心逻辑：** 识别哪些操作必须在关键路径上（ASR→LLM，因为 LLM 依赖转写文本），哪些可以后台完成（TTS、ISE 不影响文字对话）。

- 列标题用颜色区分：难点（红/橙）→ 现象 → 根因 → 解决方案（绿）→ 效果
- 底部放一句总结："关键不是让所有操作变快，而是让用户只等必须等的"

## 第 16 页：开发难点与攻克二：并发与数据一致性

### 页面标题

高并发下评分数据的可靠性，靠原子写入和 Outbox 机制保证

### 页面内容

> 以下方案已在本地通过 25 项测试（含集成测试），服务器压测待进行。

| 难点 | 现象 | 根因 | 解决方案 | 效果 |
|------|------|------|----------|------|
| **评分路径过长** | 一次词汇评分有 14 步 DB 操作 | 查→判→写模式 + 多次往返 | 词汇本/错题本改为 `INSERT ON DUPLICATE KEY UPDATE` 原子写入 | 减少 DB 往返，事务更短 |
| **并发竞态** | 同一用户并发提交可能重复计数 | "先查后写"存在时间窗口 | 唯一键 + 原子 upsert；Outbox 消费端再次去重 | 消除应用层竞态 |
| **日统计阻塞评分** | 评分接口要等进度写入才返回 | 统计与评分在同一事务 | Outbox 解耦：事务内写事件 → 后台消费 | 评分响应不再等统计 |
| **进程崩溃丢事件** | 重启后内存中的事件状态丢失 | `@Async` 无持久化 | 数据库租约（30s）+ 练习日志唯一键去重 | 至少一次、效果等同一次 |
| **学习计划无效写入** | 每次评分都 upsert 默认计划 | 没有检查已有计划 | 先查已有，仅旧用户缺计划时才创建 | 减少热路径无意义的 SQL |

**仍然保留的并发边界（诚实说明）：**

- FSRS 卡片状态（`user_word_progress`）仍为 SELECT → 计算 → SAVE，同用户同题并发评分存在覆盖风险。后续计划加乐观锁 + 有限重试。
- 同用户同一天的进度行（`user_daily_learning_progress`）仍是热点行，但锁等待已从评分 HTTP 请求中移除，仅影响后台 Outbox 消费。

### 版式建议

- 五列表格，与上一页风格一致
- 底部用独立区块列出"仍然保留的并发边界"，用蓝色而非红色标注——这些是已知限制，不是缺陷
- 标注："这些问题我们已经识别，并有后续方案"

### 讲述重点

这页体现的是**工程诚实**——既展示解决的困难，也坦诚说明已知限制。评审老师更欣赏"知道自己的边界在哪"的团队，而不是"一切都完美"的包装。Outbox 机制是团队自研实现的，值得重点展开讲。

## 备用页 C：风险与改进计划

### 页面标题

后续重点从"可用"走向"稳定、实时、可观测"

### 页面内容

**已知风险：**

- 第三方语音服务稳定性和延迟风险
- 文件 ASR 轮询模式尾部等待较长
- 自由对话中的发音评分准确性边界
- 本地文件存储不适合多实例部署
- FSRS 并发评分仍为 SELECT→计算→SAVE（无乐观锁）

**改进计划：**

- 实时 WebSocket ASR（缩短尾部等待）
- LLM SSE 流式回复（首 token 更快）
- FSRS 乐观锁 + 有限重试
- 对象存储替换本地 uploads
- 完成服务器压测报告与监控指标
- 排队模式（`queued`）生产验证

### 版式建议

- 风险用橙色三角标注
- 改进计划用蓝色箭头标注
- 诚实但不悲观——每个风险都有对应的改进计划已预研
